# Browser and accessibility evidence

The required browser workflows run with Playwright in Chromium against the Next.js development server. The CI job uses deterministic browser-intercepted API fixtures, including demo-role login and Calendar exchange/sync responses; it does not call Google or require provider credentials. The fixtures prove the browser-visible contract and interaction, not live provider connectivity or backend persistence.

The activity-log workflow runs at 320, 768, 1024, and 1440 CSS-pixel viewport widths. It exercises a Solution Architect recording project work using keyboard activation and checks accessible headings, form roles, and live feedback. The Calendar test exercises the one-time OAuth handoff, confirms the callback code is removed from the URL, sends an empty sync request (the browser does not supply a Calendar token), and checks browser storage does not contain Calendar/Google token keys. Drive tests verify that Sales can see a provisioning failure without retry rights and that Lead SA can review its details, retry by keyboard, and observe the pending attempt. Axe checks the exercised screens (and the Drive panel) against WCAG 2.1 A/AA rules.

Automated axe checks are evidence of only the rules and states exercised; they are not a WCAG conformance claim. They cannot verify that announcements are understandable at real speech rates, that focus feels logical during extended use, or that every dynamic state is exposed correctly to assistive technology. Manual validation with supported screen readers (for example NVDA with Firefox/Chrome and VoiceOver with Safari), keyboard-only use, browser zoom/reflow, and high-contrast settings remains necessary before claiming full WCAG 2.1 AA conformance. Provider and real-Drive behavior also require their separately controlled integration checks; these fixture-backed browser tests do not replace them.
